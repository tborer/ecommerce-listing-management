## Rotating eBay Deals scraping (built 2026-08-28, changed to a rotation 2026-08-29)

**Superseded the fixed CORE/EXPANSION split with a single rotating pool, Travis's 2026-08-29 decision**, so the same pages aren't scraped every single day and the daily research naturally broadens as Travis appends more URLs over time. `CORE_DEALS_URLS`/`EXPANSION_DEALS_URLS` merged into one ordered `DEALS_URL_POOL`.

**`_select_daily_urls(pool, day, pages_per_day)`**: deterministic block rotation keyed off the date's proleptic-Gregorian ordinal -- day N gets `pool[N*pages_per_day : (N+1)*pages_per_day]`, wrapping around via modulo once the pool is exhausted. No persisted cursor/state file needed; growing the pool just lengthens the natural cycle. Default `pages_per_day` = 2 (`ROTATION_PAGES_PER_DAY_DEFAULT`, CLI `--pages-per-day`) -- revised down to 2 on 2026-08-29 so each URL got dug into more thoroughly, up to 3 on 2026-09-05 alongside the pool growing with non-eBay sources, then back down to 2 on 2026-09-06 (Travis's ask): other pipeline improvements were already getting more items listed, so no need for wider daily discovery too.

**`run_pipeline()`**: scrapes+matches today's rotated pages first, counts "good" results via `_count_good()` (unchanged bar). Only scrapes+matches the *rest* of `DEALS_URL_POOL` (pool minus today's selection) if that count is below `min_good_items` (unchanged parameter/CLI flag, default `AUTO_LIST_TOP_N_DEFAULT` = 5) -- same "expand only if needed" behavior as the 2026-08-28 design, just driven by rotation instead of a fixed list. Dedupes via the same shared `seen_ids` set. `--limit` interacts the same way as before (skips the fallback expansion if already exhausted, logged distinctly).

**Pool replaced wholesale 2026-08-29 (Travis's decision)** with a wider category/site mix (17 URLs: 15 eBay Deals pages spanning tech/home-garden/automotive/fashion/sporting-goods, plus 2 non-eBay "best dropshipping products" blog URLs) so the eBay account gets a broader variety of items over the rotation cycle.

**Profit-pass formula (Steps 2/4):**
```
budget_for_supply_and_shipping = ebay_price - (ebay_price * fee_pct) - (ebay_price * margin_pct)
total_profit = ebay_price - (ebay_price * fee_pct) - aliexpress_item_price - aliexpress_shipping_cost
PASS if: aliexpress_item_price + aliexpress_shipping_cost <= budget_for_supply_and_shipping
```
`ebay_price` throughout is the Deals-page item's own price, found at Step 1 — this now doubles as the competitive-price reference too, per Step 5's deferral above (no separate lookup). `total_profit` is the email report's secondary sort key — not part of the pass/fail decision itself, just how passing results are ordered for review within each verdict group (see the Automation section for the full grouped-sort rule, updated 2026-08-26).

## Sourced-item price tracking (new requirement, 2026-08-25 — designed, not yet built, depends on Step 7)

Travis's ask: once an item is actually listed on eBay (Step 7), save a link to its AliExpress source so a recurring job can catch price drift — if the supplier raises their price after listing, the margin quietly erodes unless the eBay price gets revisited.

**Tracking-ledger entry, written at listing time (Step 7's job, once it exists)** — one record per live eBay listing, e.g. `branch11_tracked_listings.json`:
```json
{
  "ebay_listing_id": "...",
  "ebay_item_url": "...",
  "ebay_price_at_listing": 62.99,
  "aliexpress_item_url": "...",
  "aliexpress_price_at_listing": 51.65,
  "aliexpress_shipping_at_listing": 0.0,
  "fee_pct_used": 0.17,
  "margin_pct_used": 0.15,
  "date_listed": "2026-09-xx"
}
```

**Weekly check (new job, same shape as the daily one, not yet built):**
1. For each tracked listing, revisit the saved AliExpress URL and extract the current price (+shipping).
2. Compare to `aliexpress_price_at_listing`. If it moved enough to threaten the target margin (using the same `fee_pct`/`margin_pct` formula already defined), flag it.
3. Compute what the eBay price *should* be now to preserve the same margin at the new supplier cost.
4. **Report, don't auto-change** — updating a live eBay listing's price is exactly the "never create/edit/price a real eBay listing autonomously" Hard Constraint. This becomes a proposal in the recurring email (see Reporting), not an automatic price edit, until Travis says otherwise for this step specifically — same escalation pattern as Step 7 itself.
5. Suggested cadence: weekly, same 8 AM Central slot, different day (exact day not yet chosen — cheap to decide whenever this actually gets built).

**Why this can't be built yet**: there's nothing to track until Step 7 produces real listings — this is designed now so Step 7's implementation writes the ledger entry from day one rather than needing to be retrofitted later, but the weekly checker itself is genuinely blocked on Step 7 (which is blocked on eBay OAuth).

## Marketplace Account Deletion (MAD) webhook (built 2026-08-26 — required for production keys)

eBay requires this before production API keys activate — GDPR/CCPA-style compliance so eBay can tell third-party apps when a user deletes their account. The "Exempted" option doesn't apply here (Branch 11 pulls real buyer PII via `getOrders`).

**Live endpoint**: `https://node1.tailececf8.ts.net/ebay-deletion-webhook` (standard port 443 — see below for why it moved off 8443) — paste this into eBay's "Marketplace account deletion notification endpoint" field. Verification token is in the `eBay MAD Webhook` Bitwarden item (also in `ebay_mad_webhook_config.json` on disk, mode 600 — that local file is what the running service actually reads, not Bitwarden, since it must auto-start on boot with no one present to unlock the vault). **If the endpoint URL ever changes again, update both the config file and restart the systemd service** — the URL is baked into the challenge-response hash, so a stale value silently breaks verification.

**Architecture**: `branch11_ebay_deletion_webhook.py`, running as `systemctl --user` service `branch11-ebay-mad-webhook.service` (auto-restart, auto-start on boot — same pattern as the OpenClaw gateway itself). Listens on `127.0.0.1:8791`; Tailscale Funnel handles public HTTPS termination and proxies in.

**On port 443, not a separate port — a real tradeoff Travis explicitly accepted.** Originally built on port 8443 specifically to avoid touching port 443 (where the production console lives, tailnet-only) at all. **eBay's own verification service failed against 8443** (`"Client network socket disconnected before secure TLS connection was established"` — a known, common failure in eBay's developer community, consistent with their verifier expecting standard port 443). Confirmed the endpoint itself was genuinely reachable from a different network path (`WebFetch`) before concluding it was port-specific, not a broken endpoint. **Travis's explicit choice, presented with the tradeoff spelled out: move to 443, accepting the console becomes publicly network-reachable** (still protected by its own gateway auth token, but a real increase in attack surface for daily-use production infrastructure — this wasn't done as a side effect, it was a deliberate decision).

**A real incident happened while making this change — caught and fixed in the same round, logged in full in STATUS.md 2026-08-26.** Short version: `tailscale funnel --bg --https 443 443` (a bare port as the target) accidentally overwrote the console's `/` proxy target from `127.0.0.1:18789` to `127.0.0.1:443` (nonsensical). Caught by reading the command's own echoed output, not assumed. Fixed immediately with `tailscale serve --https 443 --set-path / 18789`; the underlying gateway process itself never stopped (verified via `pgrep` — same PID throughout), so this was a brief tailnet-proxy-target misdirection, not a real service outage. **Lesson for any future `tailscale serve`/`funnel` command touching this shared config: always use `--set-path <path> <target>` to modify one specific path — a bare port/URL as the positional target redefines whatever `/` currently points to.** Always verify with `serve status --json` immediately after any change, checking every existing path's target is still correct, not just that the new one applied.

**What it does**: `GET ?challenge_code=X` → returns `{"challengeResponse": sha256(X + verification_token + endpoint_url).hexdigest()}` (eBay's exact verification spec) with `Content-Type: application/json`. `POST` (real deletion notifications) → logged to `ebay_deletion_notifications.jsonl`, returns 200. No automated deletion logic — just logging + eBay's own "notify if endpoint down" email fallback.

**Confirmed working end-to-end 2026-08-26.** "Send Test Notification" succeeded in eBay's dev portal, and `ebay_deletion_notifications.jsonl` shows both real events: a `challenge_verified` with eBay's own generated challenge code, then a real `deletion_notification` POST with eBay's canonical test payload. This requirement no longer blocks production keyset activation.

## Match-judgment rubric (Step 4 — "is this actually the same item?")

Distinct from the profit-math rules above — this decides whether an AliExpress search hit is a genuine match for the eBay item at all, before the profit math is even worth running.

**Numeric `match_score` (0-100), added 2026-08-27.** `judge_match()` in `branch11_pipeline.py` computes `match_score = 100 * (0.85 * keyword_overlap + 0.15 * title_fuzzy_similarity)`, then applies subtractive penalties, then derives `verdict` from thresholds (HIGH >= 50, MEDIUM >= 30, NONE below). `keyword_overlap` is the original Jaccard-style measure (shared words / eBay title's word count); `title_fuzzy_similarity` is `difflib.SequenceMatcher` run on alphabetically-sorted token strings (not raw title order, since eBay and AliExpress titles for the same real product are often worded/ordered very differently) — kept as a minor 15% weight after testing showed a heavier weighting on it wrongly sank real matches with reordered/differently-worded titles (e.g. an Anker PowerConf speakerphone match).

| Signal | How it's used |
|---|---|
| Core product-type noun, not just shared keywords | e.g. "crate/playpen" vs. "exercise fence/kennel" are different products even sharing 5+ keywords |
| Size/scale descriptors | "small," explicit dimensions, panel/tier count — a spec mismatch (5-tier vs. 3-tier) subtracts 30 points |
| Voltage/model number (added 2026-08-27) | e.g. "M12" vs "M18", "20V" vs "18V" — a mismatch subtracts 40 points and is a hard cap (see below). Regex-based (`_VOLTAGE_RE`), not category-specific — applies to any title with a `\d+V`/`M\d+`-style token. |
| Accessory-only match (added 2026-08-27) | Ali title contains an accessory word (case/cover/holster/sleeve/skin/pouch/protector/strap/band/holder/clip/refill) that the eBay title doesn't — subtracts 45 points, hard cap. Real example this fixed: a Harman Kardon speaker matched to a *case for* that speaker. Deliberately excludes "stand"/"mount"/"dock"/"cartridge" — each is also a legitimate standalone product category, and blacklisting them produced false positives in testing (an HP docking station wrongly flagged because the Ali title said "docking station stand"; a GE water filter wrongly flagged because "cartridge" is just how filters are described). |
| Light/torch accessory (added 2026-08-27) | Ali title mentions torch/flashlight/lamp/light/led and the eBay title doesn't — subtracts 45 points, hard cap. Real example this fixed: a Milwaukee M12 battery matched to a flashlight that merely mentions compatible batteries. |
| Wired/wireless conflict (added 2026-08-27) | eBay title says wireless/bluetooth and Ali says wired, or vice versa — subtracts 35 points, hard cap. Real example this fixed: wireless Galaxy Buds3 Pro matched to unrelated wired USB-C earphones. |
| Price plausibility | A real sourceable match should price meaningfully *below* eBay's resale price; if every candidate prices at-or-above it, that's a signal of category mismatch, not just thin margin — subtracts 40 points |
| Brand authenticity (added 2026-08-29) | eBay title asserts a known brand (`_BRAND_TOKENS` — a curated list, e.g. Apple/Anker/DeWalt/Samsung, not exhaustive) as the actual product, but every occurrence of that brand in the Ali title only appears as a "for/compatible with/replacement/universal" compatibility target, or doesn't appear at all — subtracts 50 points, hard cap. Real example this fixed: a real Apple Pencil Pro ($94.99) scored HIGH against a $3.82 "Universal Stylus... For Apple Pencil" (a generic third-party knockoff, not a genuine Apple product) — the word "apple" appearing in the Ali title as a compatibility target was enough to pass the existing keyword-overlap check; this catches that a plain accessory-word check (above) doesn't, since "for Apple Pencil" isn't an accessory word, it's a brand-compatibility claim. Found live while evaluating the DSers MCP's `dsers_find_product` as a Steps 2-4 alternative — a real production risk (item-not-as-described/counterfeit-adjacent) that predated and is independent of that swap, fixed immediately in the currently-live matcher rather than deferred to whenever the swap lands.
| Construction-material mismatch (added 2026-08-31, PRODUCTION-READINESS.md Item 19) | eBay and Ali titles each assert a construction material, but from different curated clusters (`_MATERIAL_CLUSTERS` — metal/steel/aluminum/iron/alloy grouped as one cluster since they're casually synonymous in real listings, vs. separate wood/plastic/leather/fabric/glass/rattan/ceramic clusters) — subtracts 35 points, hard cap. Real examples this fixed: the original item-19 case (2026-08-25, a metal-frame dog crate matched to an Oxford-fabric item), plus 8 more found live scanning historical judged output while building this fix (a real leather dining-chair set matched to a wood-leg chair set, HIGH 71; a real aluminum laptop stand matched to a plastic laptop holder, HIGH 72; several metal/steel outdoor tables matched to aluminum ones). Clustered rather than exact-word so "aluminum" vs "steel" doesn't falsely trip the check — only a mismatch *across* clusters counts. |

**Hard-mismatch cap:** any of the six checks above (four from 2026-08-27, brand authenticity from 2026-08-29, construction-material from 2026-08-31) forces `match_score` to at most 29 regardless of how well the vocabulary otherwise overlaps — a hard product-type mismatch can never read as HIGH or MEDIUM. These are a deliberately blunt, explainable fix for specific failure patterns Travis or this branch's own testing caught in real output, not a general product classifier.

**2026-08-31, also investigated and deliberately NOT built**: a "core product-type noun" check (e.g. crate/cage/kennel vs. playpen/pen/fence/enclosure) — this table already described the *concept* as a signal, but it was never actually implemented as a coded check, and a live scan of historical judged output for real pet-containment core-noun mismatches turned up **zero cases** (unlike the material-mismatch check above, which had 9 real cases). Per this rubric's own stated principle (fixes built from real caught examples, not a general classifier), building a curated cluster list with no real evidence behind it risks introducing false positives for no proven benefit — held off. Revisit if a real example ever turns up the same way every other check here did.

**Verdict re-judged after price verification (fixed 2026-08-27):** previously, `judge_match()` ran once against noisy tile-scraped prices to pick the best candidate and assign verdict, then the product-page price-verification step (see below) replaced `prices` with the real verified price *without* re-running the rubric — so a verdict could go stale (e.g. still say HIGH after the real price made it fail the profit check outright, or vice versa). `find_best_ali_match()` now re-runs `judge_match()` against the verified price before finalizing, so `verdict`/`match_score`/`reasons` always reflect the price actually used downstream.

**Verdict tiers:**
- **HIGH** — visit the actual AliExpress product page, treat as sourceable
- **MEDIUM** — same category, spec unconfirmed — verify via product page before using
- **NONE** — reject; don't force a match onto the nearest keyword hit

Validated 2026-08-25 against two real cases (see STATUS.md Branch 11 for full detail): a hamster-cage tier-count mismatch correctly downgraded HIGH→MEDIUM, and a dog-playpen search correctly rejected (NONE) despite heavy keyword overlap, because every result was the wrong product category/size. Re-validated 2026-08-27 against the three real false-HIGH matches Travis found in email output (see above) plus a confirmed-good DeWalt battery match, and against the full 2026-08-26 candidate set as a regression check before shipping.

**eBay/AliExpress URLs (hardened 2026-08-27):** both were already canonical (no referral/tracking params) in practice, but `EBAY_TILE_JS` now builds the eBay URL directly from the scraped numeric listing id (`https://www.ebay.com/itm/<id>`) rather than the scraped anchor `href`, so it can't pick up a tracking param or path segment regardless of what eBay's markup does. The AliExpress URL was already built the same way from the extracted item id. Both fields were already present in the pipeline JSON; the email step just wasn't instructed to surface the AliExpress one (fixed in `branch11_daily_run.sh`'s prompt).

**Same-day, found via live testing while building this: two more brand-authenticity gaps in `judge_match()`'s rubric** (see the table below, "Brand authenticity" row, and STATUS.md 2026-08-29 for the real examples) — `hp`/`dell`/`lenovo`/`asus`/`acer`/`lg` added to `_BRAND_TOKENS` after a real HP docking station scored MEDIUM against an unrelated $5.60 generic game-console dock. **1. Query variations (`build_query_variations()`, up to `max_query_variations`, default 2):** tries `slug_query()`'s existing 6-word heuristic first, then `broad_query()` — a shorter (4-word), noise-stripped-from-anywhere fallback — only if the first query's results don't already judge to HIGH. A second AliExpress page load is only worth the cost when the specific query came up short.

**2. Candidate accumulation (up to `max_candidates`, default 15):** unique tile-scraped candidates (by AliExpress item id) are pooled across query variations and re-scored with the existing `judge_match()` rubric after each variation. Stops as soon as a variation yields a HIGH verdict, or once the pool hits `max_candidates` — whichever comes first.

**3. Product-page price + shipping verification (`extract_product_page_details()`):** search-tile prices are noisy — the tile's price-regex sweep over the card's text can pick up unrelated dollar amounts (bundle add-ons, "was" prices, coupon text), not just the item's real price. For a HIGH or MEDIUM verdict (matching the rubric's own existing guidance that both tiers should be confirmed via the real product page before use), makes **exactly one** attempt to visit that single best candidate's product page and pull, in one visit:
  - **Price**, from the page's schema.org `Product` JSON-LD block (`offers.price`/`offers.priceCurrency`/`offers.availability`) — confirmed live 2026-08-26 to hold a single clean price even when the same item's search tile scraped several unrelated amounts (e.g. tile `['$68.94', '$40.49', '$17.24']` vs. the real, single listed price of `$68.94`). Falls back to a visible-price DOM selector (`[class*="price-default--current"]`, a CSS-module class with a content-hash suffix — less stable across frontend deploys, kept only as a fallback) if JSON-LD is missing. On success, `AliMatch.prices` is replaced with the verified price and `AliMatch.price_verified` is set `True`.
  - **Shipping cost** (added 2026-08-26), from `.dynamic-shipping-line` (not a hashed class, confirmed stable) — its first line reads either `"Free shipping"` (→ `$0.00`) or `"Shipping: $X.XX"` (→ `X.XX`), confirmed live against both real cases. Stored on `AliMatch.shipping_cost`; `None` means the element wasn't found (unverified/unknown — **not** assumed free), and `run_pipeline()` falls back to `$0.00` in the profit calc in that case, same as the old always-zero default, with a reasons note flagging it as unverified rather than silently treating it as confirmed-free.

**On any failure (page didn't load, item pulled, selector missing), no retry** — falls back to the original tile-scraped price / unknown shipping with a reasons note and moves on to the next eBay item, per the non-exhaustive policy above.

`compute_profit()`'s `ali_shipping` argument, and its `ali_shipping_assumed` output field, now reflect this real extracted value (or the unverified $0 fallback) instead of always being the hardcoded $0 default from before 2026-08-26.

**Still not covered**: `list_candidate()` (Step 7, actual eBay listing creation) still requires `aliexpress_shipping_cost` explicitly passed in, no default — it doesn't yet read `AliMatch.shipping_cost` automatically. Wiring that up is a separate task from today's build, which only threads shipping into the daily research/report pipeline (Steps 1-4), not into listing creation.

## Category match scoring and variation skipping (built 2026-08-28)

**DECISION (Travis, 2026-08-28, via chat):** (1) surface a numerical rating of how well the auto-suggested eBay category fits the item, in the daily email; (2) skip candidates needing a Size (or other product-variation-type) value from auto-listing, since this project has no eBay Variations API (multi-size/color single-listing) support to actually offer real variants.

**Both use one real eBay signal**: `aspectConstraint.aspectEnabledForVariations` (confirmed live: `Size`/`Type` both `true`, `Brand` `false`, for the mattress-protector category) — eBay's own flag for "this required aspect is a genuine product-variation dimension," not a hardcoded name check. `get_required_aspects()` now captures it per aspect.

**`analyze_category(env, title, credential_mode)` in `branch11_ebay_listing.py`** — combined per-candidate lookup: suggests a category, computes a self-derived match-quality score (eBay's Taxonomy API has no confidence score of its own), and flags whether any required aspect is both unresolvable and variation-enabled.

**Match-score formula, two real iterations, not guessed right the first time**: v1 reused `judge_match()`'s AliExpress-matching formula verbatim (85% exact-token overlap + 15% fuzzy blob) — scored the flag item's category ("United States, Country Flags") a **0-5** despite being an excellent match, because that formula suits two similarly-shaped noun-dense titles, not a long adjective-heavy eBay title against a short category name (exact-token overlap caught nothing on "Flag" vs "Flags"; the blob-fuzzy signal got diluted by filler words like "Heavy"/"Duty"/"Luxury"). **v2 (current)**: for each word in the category's own short leaf name, take its single best fuzzy-match ratio anywhere in the title, then average -- answers "does each core category concept show up, even loosely, in the title." Re-tested against 6 cases: strong matches now 61-88 (flag item: 0-5 → 64), a deliberately nonsensical title scored lowest (35) with a visibly wrong category name alongside it. Still documented as a rough, explainable signal, not a verified-correct category — same honesty standard `suggest_category()` always carried.

**Wired into the pipeline as a real selection input, not just a report field**: `annotate_category_analysis()` in `branch11_pipeline.py` runs `analyze_category()` (credential_mode="local") for every candidate that passes the profit check (not all ~54/day scanned, to bound API volume), in `main()` right before `run_auto_listing()`. `select_auto_list_candidates()` now also excludes any candidate with `category_analysis.needs_unresolvable_variation` -- Travis's reasoning: a required Size/Color-type value with no generic option means the sourced item is genuinely multi-variant, and a single-SKU listing pinned to one arbitrary value would be a guess, not a fact.

**Verified against real data**: re-ran the full annotate+select flow against 2026-08-28's actual candidates -- all 4 remaining real HIGH+passing candidates correctly show `needs_unresolvable_variation: true` and are excluded, landing on zero auto-list picks that round (matches what should happen, not a surprise).

## Basic variant handling (built 2026-08-29) — narrow, non-exhaustive, real evidence-based

**Prompted by**: analyzing the 4 "profitable" candidates blocked by the variation-skip gate above (2026-08-29 real data) to see if any basic, non-exhaustive fix could let some real items through. **Travis's framing: doesn't need to be exhaustive, just enough to get some items flowing, extensible later.**

**Real detour found first, fixed before any variant work**: 2 of the 4 example candidates turned out to be bad AliExpress matches, not blocked-on-variants at all -- a Nespresso espresso machine matched to a $5 replacement drip tray, and a SteelSeries mic matched to a shock mount for an unrelated mic brand (Blue Yeti). Both were the exact brand-authenticity-mismatch pattern from the "Match-judgment rubric" section above; the brands (`nespresso`, `breville`, `steelseries`) just weren't in `_BRAND_TOKENS` yet (built around phone/tool/laptop examples). Added them, re-verified both now correctly score NONE, no regressions on the existing Apple Pencil/Anker/HP cases. Left as a known, unsolved harder edge case (not a confirmed bug, not fixed): the Ninja grill candidate's AliExpress match, while genuinely Ninja-branded, might be a replacement griddle/splatter-screen part rather than the whole appliance -- brand-authenticity doesn't catch same-brand-different-product-tier ambiguity, and this wasn't pursued further.

**Fuzzy/keyword-overlap matching was tested and rejected for aspect-value selection** -- reused `analyze_category()`'s existing per-word fuzzy-match formula (proven fine for coarse category-fit scoring) against the iPad folio case's real `Type` options, and it picked **"Back Cover"** as the top match purely from scattered word overlap ("...Protective **Back** ... Leather ... **Cover**...", two words from unrelated parts of the title), when the item is really more of a folio case. Picking a specific wrong enum value on a real live listing is exactly the risk this project avoids -- concluded fuzzy matching isn't precise enough for this and dropped it from the design. Only literal, narrow mechanisms below made the cut.

**Two new resolution tiers in `_resolve_aspect_value()` (`branch11_ebay_listing.py`), tried after the existing generic-value tier (`_generic_aspect_value()`, unchanged) and only for non-Brand aspects:**
1. **Closed-enum tier**: if one of eBay's own suggested values for the aspect literally appears (whole-word, case-insensitive) in `ali_text` -- the AliExpress match's own title+description, **never the eBay comparable** -- use it. Still only ever a value eBay itself vouches for as valid, just sourced from real item text instead of a fixed generic. Excludes an occurrence immediately preceded by a compatibility qualifier ("for"/"fits"/"compatible"/"replacement"/"universal", same set `_brand_authenticity_mismatch()` uses in `branch11_pipeline.py`) -- e.g. "Shock Mount **for Blue Yeti** Mic" must never read "Blue" as this item's own Color.
2. **Free-text tier, "Model" aspect only**: for categories where eBay's own suggested `values` sample is clearly just OTHER listings' unrelated model numbers (confirmed live 2026-08-29: a real espresso-machine category's "Model" aspect suggested values were De'Longhi/Lelit/Magnifica -- zero Nespresso models at all; same pattern for a real grill category, suggesting Bosch/Hamilton Beach/Tefal instead of any Ninja model) -- genuinely an open text field, not a closed enum for this item. `_extract_model_token()` pulls the first alphanumeric, letter-and-digit-mixed token (e.g. "AG301", "EC9665.M") from `ali_text` not preceded by a compatibility qualifier -- a real model/part number the actual shipped item's own title states about itself.

**Why sourcing from `ali_text` (the AliExpress match) rather than the eBay comparable's title matters, not just a style choice**: `list_candidate()` already builds the actual listing's title/description exclusively from the AliExpress match (see "Listing title and images" below) specifically because the eBay comparable's title can name a brand/model that isn't what's actually being shipped. Sourcing aspect values the same way keeps that same honesty guarantee -- an aspect value describes the real AliExpress-sourced item, never borrows identity from the branded eBay listing being priced against.

**Brand stays fully excluded from both new tiers** -- unchanged "Unbranded"-only behavior. Brand is an identity/provenance claim; the 2026-08-28 "Sony matched from 'compatible with Sony PS5' text" incident (see `build_item_aspects()`'s docstring) is exactly why. Color/Connectivity/Type/Model are physical/descriptive attributes, not provenance claims, which is what makes text-matching them safe where matching Brand wasn't.

**`analyze_category()` gained an `ali_text` parameter** (default `""`, safe no-op for any caller not yet passing it) so the auto-list eligibility check (`needs_unresolvable_variation`) uses the exact same resolution logic as actual listing creation (`build_item_aspects()`) -- previously these could theoretically disagree, since eligibility-checking only ever used the generic-value tier. `annotate_category_analysis()` in `branch11_pipeline.py` now passes `best_ali_match.title + description` as `ali_text`.

**Validated live against real eBay production categories, both directions**: the Ninja grill's real `Model` aspect (category 20675) resolved to `AG301` (extracted from its real AliExpress match's title) via both `build_item_aspects()` (`{"Brand": ["Unbranded"], "Model": ["AG301"]}`) and `analyze_category()` (`needs_unresolvable_variation` flipped from `True` to `False`) -- confirming the two stay in agreement. The iPad folio's real `Type` aspect (category 176973) correctly stayed unresolved (`None`) in both -- no literal enum-value match exists in its real AliExpress match's title, and the mechanism deliberately doesn't force one.

**Explicitly not exhaustive, by design** -- covers exactly the two real patterns found so far (closed-enum literal match, Model free-text extraction). Real, known gaps left for later: `Type`-style aspects with no literal match (the iPad folio case) stay blocked; same-brand-different-product-tier ambiguity (the Ninja grill's whole-appliance-vs-replacement-part question) isn't addressed at all; only tested against 2 real categories so far, not a broad sample. Extend the same way `_BRAND_TOKENS`/`_ACCESSORY_WORDS` have been extended -- as new real cases turn up, not speculatively ahead of evidence.

## Listing title and images (decided/investigated 2026-08-27)

**Listing title uses the AliExpress match's own title, not the eBay Deals-page item's title.** Travis's decision, prompted directly by the brand-mismatch matches found in the 2026-08-27 review (Buds3 Pro → generic unbranded earbuds, Anker PowerConf → generic mini speaker): using the eBay item's title risks naming a specific brand/model for a sourced item that isn't actually that product. **Listing description uses the AliExpress match's own description — decided and implemented 2026-08-27.** Same reasoning as the title: it describes what's actually being shipped, keeping the listing honest even when the research-stage match is imperfect. Confirmed live that AliExpress product pages' `ld+json` `Product` block (the same one already used for price) also carries a clean `description` field, at zero extra page-visit cost -- `PRODUCT_PAGE_JS`/`AliMatch`/`find_best_ali_match()` in `branch11_pipeline.py` all updated to capture it during the existing product-page verification visit. `list_candidate()` now uses it for both `create_inventory_item`'s `product.description` and `create_offer`'s `listingDescription` (both previously said "Sourced item, see {ebay competitor URL}..."), and refuses to proceed (flags for manual review) if a candidate has no captured description -- same hard-stop pattern as the title. **No fallback/default text** -- an unverified description should block, not silently ship something unreviewed. **Candidate files predating 2026-08-27 don't have this field** and will hit the block until re-run or backfilled for the specific candidate being listed.

**Description scrubbing — decided and implemented 2026-08-29, extended twice same day.** Before the AliExpress description is used anywhere, `scrub_description()` (`branch11_ebay_listing.py`) strips five terms, whole-word/case-insensitive: **"AliExpress"** (would reveal the dropship source to the buyer), **"Free"** (risks reading as an unadvertised free-shipping/free-item claim eBay didn't actually configure on the listing), **"Returns"/"Return"** (avoids the description making a returns claim that conflicts with the account's actual return policy), and **"Worldwide"** (added after the first two manual listings went live still carrying "Shipping Worldwide! ... Whitespace/punctuation left behind by the removal is collapsed so the result doesn't read as visibly mangled (double spaces, dangling `" ,"`). Wired into `list_candidate()` right where `listing_description` is built, so it covers both the autonomous top-N path and manual chat-approved SKU listings — there's no separate code path that could skip it. Only the description is scrubbed, not the title (Travis's ask was scoped to description).

**Images: point directly at the AliExpress product image URL, not a separate re-hosting step.** `list_candidate()` already does this (`ali_match.get("imageUrl")`, captured during the AliExpress tile scrape) -- eBay's Inventory API only accepts an image *URL* (no direct binary upload in the modern REST Sell APIs; that's a legacy Trading API-only mechanism), fetches/imports it itself, and hosts its own copy via EPS at creation/publish time -- so this is the correct, intended mechanism, not a workaround.

**AVIF question — empirically confirmed 2026-08-27, sandbox-side.** `create_inventory_item('sandbox', ...)` with a real AliExpress `.avif` URL (from candidate `branch11-394792332187`) returned `204`; reading the item back showed the URL stored verbatim in `imageUrls`, no format-rejection anywhere in the chain. Matches the two independent web searches that indicated eBay's Media API lists AVIF among its supported formats. **Not fully closed**: this confirms the Inventory API *accepts* the URL, not that EPS renders/hosts a real image copy end-to-end -- that's only visible on a *published* listing, and `publish_offer` is the known-broken sandbox step below. **Still worth a visual glance during the one deliberate production `publish_offer` test (next-steps item 17)** to confirm the image actually renders, but the format-rejection risk that motivated this item is resolved.
